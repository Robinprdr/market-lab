# OPG / MOC without a continuous local session — preparation only

Decision dated 2026-10-09. Exact Paper account DUR231204, one AAPL share, no strategy signal, no LIVE. No order was sent for this analysis. The three-checkpoint CLI is now implemented; real disconnected auction execution remains unvalidated. See AUCTION_VALIDATION.md for the current commands.

## Decision and documentary evidence

Use separate, short sessions: OPG submission, confirmed-entry reconciliation and MOC submission, then final reconciliation. Do not pre-submit an independent SELL MOC while flat. Do not adopt an OPG parent + MOC child as a proven architecture yet.

[Current IBKR bracket documentation](https://ibkrcampus.com/docs/general/order-types/complex-orders/bracket-orders) describes parent/child linking and coordinated transmission: staging orders with Transmit=False is temporary, and the final child with Transmit=True triggers transmission of the family. The example uses LMT profit-taking and STP protection. It does not explicitly confirm the exact LMT/OPG parent + MOC/DAY child combination, its cancellation/expiry handling or Paper behavior with Gateway shut down. That combination is **unconfirmed, not declared unsupported**. A parentId alone is not documentary proof of these guarantees.

[IBKR order-placement guidance](https://ibkrcampus.com/campus/trading-lessons/python-placing-orders/?retakeFinal=1) recommends checking complex combinations in TWS before API use. If this family is revisited, first inspect the Paper TWS ticket without transmitting, then obtain authoritative confirmation for AAPL's exchange and current API/TWS versions. Do not use two independent orders or a time condition as a substitute for an execution-dependent child.

[Current API transmission documentation](https://www.interactivebrokers.com/docs/tws-api/doc/orders/place-order/introduction) says untransmitted orders remain in the TWS session and are cleared on restart. Every selected standalone order must therefore use Transmit=True and be confirmed remotely before intentionally disconnecting. A local placeOrder call or PendingSubmit alone is insufficient.

[Current error-code documentation](https://www.interactivebrokers.com/docs/tws-api/doc/error-handling/error-codes) requires DAY for MOC/LOC (113) and restricts conditional submissions (148) to specified order types that do not include MOC. This conditional-order restriction is not a blanket prohibition of parent-linked MOC orders. No assumptions about reduce-only protection for US stock MOC orders are made.

[IBKR documents Nasdaq LOO submission before 09:28 ET](https://www.interactivebrokers.co.in/en/trading/ordertypes.php). Submit AAPL OPG around 09:20 ET, with a conservative local deadline of 09:25 ET. The previous harness's 09:30 cutoff is too permissive for this disconnected protocol. [IBKR's MOC lesson](https://www.interactivebrokers.eu/campus/trading-lessons/ibkr-desktop-market-on-close-order/) lists Nasdaq 15:55 and NYSE 15:50 ET; retain the existing stricter close-minus-60-minutes cutoff and submit MOC shortly after the opening fill. Early closes use the exchange session calendar, not a hard-coded 16:00.

## Persistence: what is and is not established

Python/Codex need not calculate a trigger or submit an order at auction time after a valid standalone order is transmitted and acknowledged by the broker. Broker/exchange execution, not the local process, is intended to drive the auction order. Local SQLite will be stale during disconnection and must not be displayed as freshly reconciled.

Gateway/TWS is required for each socket API connection, submission and account/execution retrieval. The [official legacy connection-error documentation](https://interactivebrokers.github.io/tws-api/message_codes.html) describes continued operation of native orders during broker maintenance, with execution reports/simulated orders delayed. It is deprecated and does **not** prove that this Paper workflow fills with Gateway closed. [IBKR's Paper account lesson](https://www.interactivebrokers.com/campus/trading-lessons/signing-up-for-a-paper-trading-account/) confirms that Paper orders do not execute on an exchange or clear there. Live/native persistence must not be promoted into a guarantee about the Paper simulator.

Accordingly: continuous Python/Codex is unnecessary in the proposed design; complete independence from an open Gateway/Mac remains an empirical acceptance criterion. Do not promise it from these documents alone. If that criterion fails, the strict Mac-off requirement is not satisfied; stop and retain diagnostics rather than silently leave Gateway running or change order types. A stable remote host would be a separate deployment mission, not part of this preparation.

## Exact proposed test protocol (not executed)

1. Select one normal NYSE/Nasdaq session on which the operator can reconnect briefly after opening. For 2026-10-09: 09:20 ET is 23:20 Brisbane on Friday; 09:35 ET is 23:35 Brisbane; 16:10 ET is 06:10 Brisbane on Saturday 2026-10-10. The morning checkpoint is essential; there is no fully unattended parent/child round trip approved here.
2. At about 09:20 ET, connect Gateway Paper on localhost:4002 with dedicated client 82. Confirm exact DUR231204, verified settled USD, fresh reconciliation, zero positions, zero open orders from all API clients, no active ambiguous SQLite intent. Persist one PAPER_TEST_OPG BUY intent before network I/O. Use AAPL STK/USD, quantity 1, LMT, OPG, outsideRth=False, Transmit=True. Calculate the test limit from a verified prior completed unadjusted close, respecting risk controls and any genuinely current broker ceiling. Do not reuse an old rejection ceiling. Do not send after 09:25 ET.
3. Record acknowledgement, broker order ID, nonzero permId, terms and ET/UTC timestamps. Close Python; reconnect briefly and fetch open orders to verify that the exact transmitted order persists. A missing order requires executions/completed-order inspection, not a fresh submission. After persistence is confirmed, close Gateway and the Mac/network for the auction interval if testing the full Mac-off requirement. This is an explicit Paper persistence experiment, not an already-proven feature.
4. At about 09:35 ET, reconnect. Retrieve executions, completed/open orders and actual positions. Deduplicate execution IDs and update the original SQLite intent/position. Only an identified BUY fill of exactly one AAPL share, IBKR position +1, matching SQLite position and reconciliation PASS permit the next step. Check the execution time is consistent with opening, not an ordinary-session fill. If there is no confirmed fill, send **no SELL**. If the OPG remains working after the opening, stop the test and resolve/cancel that known order with broker confirmation; do not leave it unattended or resubmit.
5. Still in this short session, verify no other exit order and that the position belongs to this test. Persist one PAPER_TEST_MOC SELL intent linked in the ledger to the confirmed entry execution. Send quantity 1, MOC, DAY, Transmit=True; no parentId dependency is needed because the long position already exists. Confirm accepted terms, nonzero permId and persistence after Python reconnect. No MARKET fallback. A rejection/uncertain submission means STOP: the one-share Paper long may remain and must be reported unresolved. No blind retry.
6. Close Python and, for the separate Gateway-off experiment, Gateway/network. Do not sell or alter this position through another client during the gap: an accepted standalone MOC is not a reduce-only guarantee and must not become an unmatched sell. A local stop/kill file cannot cancel a transmitted server order while offline.
7. Reconnect around 16:10 ET, preferably within the same ET trading date. Retrieve SELL execution, commission, execution time, completed/open orders and positions. Update SQLite by execution ID, verify quantity 1 exited, no open order, no position, final reconciliation PASS. Do not infer a fill from an order's disappearance. If later retrieval omits executions, obtain an auditable broker trade report; never synthesize a fill from position balance alone.
8. Report separate OPG, MOC, Python-disconnect and Gateway-off outcomes. A fill without the required disconnection does not validate Mac-off operation. Both orders surviving each planned disconnect with correct fills and final flat reconciliation are required before claiming the workflow is validated.

## Implementation status

The continuous runner has been replaced by `enter`, `arm-exit` and `verify-close`. The implementation persists reserved IDs before network I/O, recovers authoritative broker acknowledgements/executions, blocks unresolved states and uses read-only final verification. Tests cover restart, stale SQLite, lost acknowledgements, missing fills, duplicate exits, deadlines and account/mode guards. See AUCTION_VALIDATION.md for exact commands and operational limitations. No API order was sent during implementation.

## Residual risk

OPG may not fill, MOC may be rejected/expire, Paper execution may require an active Gateway, and broker outages can leave an already-filled long unresolved. There is also a position-check-to-submit race if another client changes the position. Keep the Paper account exclusively dedicated to this one-share test with no concurrent writer. The design avoids a planned SELL while flat; it cannot guarantee zero risk under arbitrary broker failures or external account changes. No unattended short-producing fallback is permitted.
